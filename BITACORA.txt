2. DECISIONES DE ARQUITECTURA Y DESPLIEGUE
--------------------------------------------------------------------------------

2.1 Monorepo, no multirepo
    Se mantiene un unico repositorio para backend, frontend y movil.
    Razon: microservicios exige independencia de despliegue y de base de datos,
    no de repositorio. Separar en 11 repos obligaria a publicar medcore-commons
    como artefacto versionado en un registry y a bumpear 11 poms por cada cambio,
    ademas de 14 pipelines y 14 juegos de secretos.

2.2 Sin repositorio medcore-config
    La guia pedia un repo privado aparte que el Config Server clonara en
    produccion. Se descarta.
    Razon: el Config Server corre siempre en modo native leyendo
    infra/config-repo/ desde disco. Esto elimina el token de GitHub, su
    expiracion, y un modo de falla el dia de la demostracion. Un solo repo.

2.3 Despliegue hibrido: backend local + frontend en Vercel
    Se evaluo Render para el backend y se descarto.
    Razon: el plan gratuito da 512 MB de RAM y 0.1 CPU por instancia, suspende
    tras 15 minutos sin trafico (lo que desregistra los servicios de Eureka), su
    Postgres gratuito expira a los 30 dias, y los Features on Demand de Kafka
    gratuitos ya no existen (Upstash Kafka discontinuado; Aiven free solo
    permite 5 topicos y el proyecto necesita 9).

    Modelo adoptado:
      [Navegador] --HTTPS--> [Vercel: medcore-frontend]
                                   |  VITE_API_BASE_URL
                                   v
                          [ngrok: dominio estatico]
                                   |
                                   v
                 [laptop: docker compose, solo :8080 expuesto]

    Ventajas: se recuperan Eureka y Config Server (la arquitectura completa de
    la guia queda demostrable), Kafka KRaft local con los 9 topicos, las 7 bases
    Postgres locales, sin limites de RAM ni arranques en frio.

    Reglas del despliegue:
      - Por el tunel se expone UNICAMENTE el 8080 del gateway.
        Nunca 8761, 5432, 27017 ni 9092.
      - El dominio de ngrok debe ser estatico y reservado: la URL se compila
        dentro del build de Vercel y dentro del APK.
      - En dominios gratuitos ngrok devuelve una pagina intersticial a los
        user-agent de navegador. El cliente HTTP debe enviar la cabecera
        ngrok-skip-browser-warning: true, o recibe HTML en vez de JSON.
      - CORS en el gateway con allowed-origins: ${FRONTEND_ORIGIN}.
      - JWT_SECRET de produccion con openssl rand -base64 64.

2.4 Versiones de Spring (verificadas en repo1.maven.org)
    Se descarto Spring Boot 4.1.1 pese a ser estable.
    Razon: ningun tren estable de Spring Cloud apunta a Boot 4.1.x.
      Spring Cloud 2025.1.4    -> spring-boot.version 4.0.9
      Spring Cloud 2026.0.0-RC1 -> spring-boot.version 4.2.0-RC1
    Como la arquitectura depende de Eureka, Config Server, Gateway y OpenFeign,
    manda el tren de Spring Cloud.

    Adoptado:  Spring Boot 4.0.9 + Spring Cloud 2025.1.4

      spring-cloud-config         5.0.6

    IMPORTANTE: el starter del gateway se renombro en la rama 5.x.
      Correcto:   spring-cloud-starter-gateway-server-webflux

4. PROBLEMAS ENCONTRADOS Y RESUELTOS
--------------------------------------------------------------------------------

4.1 InvalidConfigDataPropertyException en config-server
    Se habia puesto spring.profiles.active: native dentro de
    application-local.yml. Spring Boot prohibe fijar el perfil activo desde un
    archivo especifico de perfil. Resuelto con spring.profiles.group en
    application.yml, mapeando local a native y prod a native.

4.2 PlaceholderResolutionException en el gateway
    La anotacion Value sobre gateway.rutas-publicas fallaba. El config-server
    entrega las listas YAML como claves indexadas (gateway.rutas-publicas[0],
    [1], ...) y no existe la clave plana; solo el binder de
    ConfigurationProperties sabe reconstruir la lista. Resuelto con la clase
    GatewayProperties.

4.3 Jackson 3 en Spring Boot 4
    spring.jackson.serialization.write-dates-as-timestamps rompia el arranque
    con "No enum constant tools.jackson.databind.SerializationFeature...".
    En Jackson 3 el paquete es tools.jackson y esa opcion salio de
    SerializationFeature hacia DateTimeFeature. Se elimino: el valor por
    defecto de Jackson 3 ya es ISO-8601.

4.4 requestId ausente en los errores de enrutamiento
    El GatewayExceptionHandler recibe el exchange original, no el que mutó el
    filtro, asi que no veia la cabecera X-Request-Id. Resuelto guardandolo
    como atributo del exchange.

4.5 Error 503 generico
    Los errores por falta de instancia salian como ERROR_GATEWAY. Ahora se
    distinguen SERVICIO_NO_DISPONIBLE, LIMITE_PETICIONES y RUTA_NO_ENCONTRADA.

4.6 CRLF en el Makefile
    Con SHELL igual a /bin/bash, un Makefile entregado con CRLF hace fallar
    las recetas. Se agrego a .gitattributes junto a *.mk.

--------------------------------------------------------------------------------
1. AUTH-SERVICE (:8081)
--------------------------------------------------------------------------------

1.1 Modelo
    User, Role y SessionLog, con migraciones Flyway V1 y V2.
    Indice unico PARCIAL sobre id_paciente: un paciente no puede tener dos
    cuentas, pero los usuarios internos repiten NULL sin chocar.
    Indice sobre LOWER(correo) para que el login no distinga mayusculas.
    session_log registra tanto los accesos correctos como los fallidos: una
    racha de fallos desde una misma IP delata un ataque de fuerza bruta.

1.2 Autenticacion
    Login por DNI o por correo en el mismo campo. Refresh con rotacion: cada
    renovacion emite un refresh nuevo, de modo que un token robado tenga una
    ventana de uso acotada. Logout revoca en Redis.

    La lista negra guarda el jti, no el token entero, con TTL igual a la
    vigencia restante: Redis libera la clave sola cuando el token ya no
    serviria de todas formas, y la lista no crece sin limite.

1.3 Decisiones de seguridad
    Usuario inexistente y contrasena incorrecta devuelven el MISMO error,
    CREDENCIALES_INVALIDAS. Mensajes distintos permitirian averiguar que DNI
    estan registrados en la clinica.

    Cuando el usuario no existe se cifra igualmente contra un hash ficticio,
    para que el tiempo de respuesta no delate su existencia.

    AdminBootstrap crea el ADMIN inicial solo si no hay ninguno, con la
    contrasena de ADMIN_INITIAL_PASSWORD o una aleatoria que se muestra una
    sola vez en el log. No se versiona ningun hash conocido en el repositorio:
    cualquiera que clonara el proyecto podria entrar como administrador.

1.4 Resultados
    18 tests unitarios. Verificado contra Postgres y Redis reales.


--------------------------------------------------------------------------------
2. PATIENT-SERVICE (:8082)
--------------------------------------------------------------------------------

2.1 Modelo
    Patient y MedicalHistory, con migraciones V1 y V2.
    La edad NO se almacena: se calcula al responder, porque una edad guardada
    queda obsoleta al dia siguiente del cumpleanos. Filtrar por edad se
    traduce a un rango de fechas de nacimiento, asi la consulta aprovecha el
    indice.

    Indice unico PARCIAL sobre (origen, referencia_externa) en el historial,
    para que un reintento del servicio de origen no duplique un episodio.

2.2 Sin Redis ni jjwt
    Decision deliberada, y coincide con la seccion 3.3 de la guia.
    jjwt solo lo necesita quien emite tokens (auth-service) o verifica su
    firma (api-gateway). patient-service confia en las cabeceras del gateway
    (MC4). Incluirlo seria codigo muerto e invitaria a duplicar la logica de
    seguridad en ocho servicios.
    Redis no se usa porque no hay nada que cachear; con el starter presente,
    Spring intentaria conectar al arrancar y fallaria el healthcheck por una
    dependencia que no se usa.

2.3 Decisiones de diseno
    El DNI se ignora al actualizar: cambiarlo equivaldria a sustituir a la
    persona de la ficha y dejaria su historial atribuido a otra.

    Las fichas no se borran. Un historial clinico es un registro que debe
    conservarse; dar de baja solo la saca de las busquedas operativas. Una
    ficha cerrada por fallecimiento no se reabre.

    El listado devuelve PatientSummaryResponse, de seis campos. Una busqueda
    que devuelve cien pacientes no debe transportar direcciones, alergias ni
    contactos de emergencia.

    PatientSpecification en lugar de metodos derivados: con seis criterios
    opcionales y combinables harian falta decenas de metodos en el repositorio.

2.4 Eventos publicados tras el commit, no dentro de la transaccion
    publicarTrasCommit registra una TransactionSynchronization y publica en
    afterCommit. Publicar dentro de la transaccion permitiria que auth-service
    reciba el patient.created y consulte un paciente que todavia no existe, o
    que la transaccion revierta despues y quede un evento de un paciente que
    nunca se registro.

    Se publica con el DNI como clave de particion, para que todos los eventos
    de un mismo paciente vayan a la misma particion y lleguen en orden: sin
    eso, un patient.updated podria procesarse antes que su patient.created.

3.2 Bug de transacciones en el bloqueo de cuentas
    El contador de intentos fallidos y la fila de auditoria se guardaban en la
    misma transaccion que despues lanzaba la excepcion de credenciales. El
    rollback los revertia: la cuenta NUNCA llegaba a bloquearse y los intentos
    fallidos no quedaban registrados.

    Solo aparecio al ejecutar el servicio de verdad; los tests con mocks no lo
    habrian detectado. Resuelto con AuthAuditService y
    @Transactional(propagation = REQUIRES_NEW). Al ser un bean distinto, la
    llamada pasa por el proxy de Spring; en la misma clase la propagacion se
    ignoraria.

3.3 anyLong() de Mockito no coincide con null
    El usuario de prueba no tenia id, el stub no se aplicaba y el test fallaba
    por una razon distinta a la real. Resuelto con ReflectionTestUtils.

--------------------------------------------------------------------------------
1. EL PROBLEMA CENTRAL: LA DOBLE RESERVA
--------------------------------------------------------------------------------

Dos pacientes piden el mismo horario a la vez. Si ambos ganan, el medico
tiene dos citas superpuestas y alguien se queda sin atender.

Se resolvio con TRES capas, de la mas interna a la mas externa:

1.1 Indice unico (id_medico, fecha, hora_inicio) en time_slots
    Impide que existan dos franjas identicas. Protege sobre todo al generador
    de slots: si se reejecuta, no duplica la agenda.

1.2 Bloqueo pesimista al reservar
    TimeSlotRepository.buscarParaReservar usa @Lock(PESSIMISTIC_WRITE), que
    se traduce en SELECT ... FOR UPDATE, con timeout de 5 segundos.

    Dos peticiones simultaneas quedan SERIALIZADAS: la segunda espera a que
    la primera confirme y entonces ve el slot ya ocupado, de modo que recibe
    409 HORARIO_OCUPADO, un error de dominio claro.

    Se eligio pesimista y no optimista a proposito. Con solo @Version, la
    segunda peticion fallaria con OptimisticLockingFailureException, un error
    tecnico que el usuario no entiende y que no distingue "ya lo reservaron"
    de "hubo un problema".

1.3 Indice unico parcial ux_appointment_slot_activa
    Sobre appointments(id_slot) WHERE estado IN ('SCHEDULED','CONFIRMED').
    Es la red de seguridad si hubiera dos instancias del servicio. Es PARCIAL
    para que, al anular una cita, el slot pueda reservarse de nuevo sin
    chocar con la fila anulada.

VERIFICADO con una carrera real: dos POST simultaneos sobre el mismo slot.
  Peticion A -> RESERVADA cita 2
  Peticion B -> RECHAZADA HORARIO_OCUPADO http 409
  Base de datos: 1 sola cita viva sobre ese slot.


--------------------------------------------------------------------------------
2. OTRAS DECISIONES DE DISENO
--------------------------------------------------------------------------------

2.1 Orden de los pasos al reservar
    El paciente se valida ANTES de tomar el bloqueo. Llamar a patient-service
    con el slot ya bloqueado mantendria el bloqueo abierto durante toda la
    llamada de red y bloquearia a los demas durante cientos de milisegundos.

2.2 Si patient-service no responde, NO se reserva
    El fallback de Feign lanza PACIENTE_NO_VERIFICABLE (503). Reservar a
    ciegas crearia una cita contra un paciente que quiza no existe o cuya
    ficha esta cerrada, y habria que deshacerla a mano. Se prefiere rechazar
    y que recepcion reintente.

2.3 Las transiciones de estado viven en AppointmentStatus
    siguientesValidos() las declara en un solo sitio. Repartirlas por el
    servicio llevaria a que dos metodos se contradigan.

2.4 NO_SHOW no libera la franja
    El horario se consumio aunque el paciente no acudiera. Liberarlo
    permitiria reservar una hora ya pasada.

2.5 CANCELLED si la libera
    Al anular con antelacion, la franja vuelve a estar disponible para otro
    paciente, que es el objetivo de exigir un plazo minimo de cancelacion.

2.6 EMERGENCY ocupa dos franjas CONSECUTIVAS
    Se verifica que la siguiente empiece exactamente donde acaba la primera.
    Si solo se comprobara que hay dos libres, la urgencia podria partirse en
    dos tramos con otra cita en medio.

2.7 La cita copia el nombre y el contacto del paciente
    Duplicacion deliberada: evita llamar a patient-service para listar la
    agenda del dia, que es la consulta mas frecuente, y deja constancia de
    con que datos se reservo. Por eso PatientEventConsumer no actualiza las
    citas ya creadas cuando el paciente cambia sus datos: la cita de la
    semana pasada debe seguir mostrando con que telefono se reservo.

2.8 La cache de Redis no es la fuente de verdad
    Si Redis cae, invalidarCache traga la excepcion y la disponibilidad se
    sigue leyendo de la base. Una cache caida no debe detener las reservas.
